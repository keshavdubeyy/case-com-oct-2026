## 2. Cohorts

Per `README.txt` and confirmed in `episode_outcomes.csv`:

- **DEVELOPMENT**: `consult_date <= 2026-06-30` → 4,132 episodes. `lost_to_followup_label` and `dropout_stage_label` populated (0% null within cohort).
- **EVALUATION**: `consult_date` 2026-07-01 → 2026-08-15 → 1,384 episodes. Both label columns are **blank** (100% null within cohort) — organizer-retained. `dropout_stage_label` distribution within DEVELOPMENT: Completed care journey 2,144, Medicine not collected 1,170, Review not attended 543, Test not completed 275 (sums to 4,132, confirming the stage label is mutually exclusive and exhaustive for DEVELOPMENT).
- `teleconsultations.consult_date` spans 2026-01-01 → 2026-08-15, i.e. it covers both cohorts (DEVELOPMENT dates go up to 2026-06-30; EVALUATION dates start 2026-07-01) — consistent.
- **Dashboard rule**: EVALUATION rows are shown as volume/context only. No chart ever computes an LTFU rate, dropout-stage split, or any rate keyed on `lost_to_followup_label`/`dropout_stage_label` using EVALUATION rows — those two fields are blank there and must never be back-filled, imputed, or treated as "0/negative".

## 4. Patient-entity linkage problem

`patient_360_reference.csv` is the only canonical patient table (`patient_id`, 5,000 unique). Every operational table instead carries its own **source-system-local** ID, explicitly documented as having "No direct crosswalk supplied":

| File | Source ID column | Rows | Distinct IDs | Rows/ID |
|---|---|---:|---:|---:|
| teleconsultations.csv | tele_source_patient_id | 5,516 | 4,231 | 1.30 |
| ncd_screening.csv | ncd_source_patient_id | 4,748 | 3,589 | 1.32 |
| prescriptions.csv | rx_source_patient_id | 5,151 | 3,449 | 1.49 |
| medicine_dispensing.csv | pharm_source_patient_id | 3,756 | 2,781 | 1.35 |
| lab_tests.csv | lab_source_patient_id | 2,005 | 1,814 | 1.11 |
| followup_visits.csv | visit_source_patient_id | 2,575 | 2,270 | 1.13 |
| visit_history.csv | visit_source_patient_id | 13,061 | 4,747 | 2.75 |
| outreach_actions.csv | outreach_source_patient_id | 6,088 | 2,705 | 2.25 |

None of these IDs may be assumed equal to `patient_360_reference.patient_id`, nor equal to each other across files, nor even trusted as a stable per-patient key *within* a file, without going through linkage. Each source table also carries noisy identity fields that must be used for matching, not taken at face value: `patient_name` (typos, name-order variants — 5,000 canonical patients collapse to as few as ~800–1,700 distinct name strings per table, i.e. heavy repetition/collision, so name alone is not a key), `mobile` (7–8% null, formatting differences, and `patient_360` only exposes the **last 4 digits** via `masked_mobile`, so exact mobile matching is only possible on the last-4-digit suffix), `age` (source age vs. reference `age_as_of_2026`, may differ by ±1–2 years), `village` (113 free-text variants across operational tables vs. 36 canonical villages in `geography_reference` — spelling noise, not real village diversity), and `gender`.

**Linkage strategy** (implemented in `scripts/linkage.py`, see `METRICS.md` §Linkage for the scoring formula): block candidates by (gender, normalized-village-token, age within ±2y), score surviving candidates on name similarity + mobile-last-4 match + village match + age closeness, and only accept a match above a confidence threshold. Every resolved link keeps its `confidence` score and `method`; episodes/records that don't clear the threshold are left **unmatched** rather than forced onto a best-guess patient — this is the explicit rule from the brief ("do not fabricate a canonical patient match when confidence is low") and is enforced in code, not just in the writeup.

**Practical consequence for the dashboard**: episode-level metrics that only need fields already present on `teleconsultations`/`episode_outcomes`/`prescriptions`/`medicine_dispensing`/`followup_visits`/`outreach_actions` (which is most of the Care Journey, Dropout, Medicine Access, Follow-up Review, and Geography pages, since `district`/`block`/`village`/`distance_to_facility_km`/`connectivity_quality` are all recorded directly on `teleconsultations`) **do not depend on patient-entity resolution at all** and carry no linkage uncertainty. Only patient-level segment rollups (vulnerability_group, household, canonical NCD status, cross-episode history for the same real person) and the two standalone streams (`ncd_screening`, `lab_tests`, cross-system history in `visit_history`) depend on the fuzzy linkage step, and that dependency — plus its confidence — is surfaced explicitly on the Data Quality & Record Linkage page rather than silently assumed.

## 5. `visit_history.csv` — internal structure

`visit_type` breakdown: Teleconsultation 5,516 (mirrors every `teleconsultations` row, `episode_id` populated), Follow-up review 2,575 (mirrors `followup_visits`, `episode_id` populated), NCD follow-up 1,699 / Screening visit 1,639 / OPD visit 1,632 (episode_id **null** — these are the "prior healthcare engagement" rows used for historical-behavior features, and they only resolve to a patient via `visit_source_patient_id`, not via any episode). `episode_id` null rate is 38.05% = 4,970 / 13,061, exactly matching 1,699+1,639+1,632. `visit_date` range extends back to 2025-07-01, well before the earliest `consult_date` (2026-01-01) — enough pre-period history exists to build lookback windows (30/60/90-day prior-visit counts) without truncation at the start of the observation window for episodes early in 2026.

## 6. Data-quality issues worth flagging on the Data Quality page

- `known_ncd_status` (patient_360) null 42.7% — legitimate "no known condition," not missing data; must not be treated as a data-quality defect.
- `mobile` null ~7–8% across every operational table with a mobile column — consistent rate, likely a simulated missingness process, relevant to outreach contactability analysis.
- `review_due_days` (teleconsultations) null 31.96%, exactly matching `review_advised == 'No'` count (1,763) — a clean eligibility signal, not missing data.
- `ncd_status`/`control_status`/`next_followup_due` (ncd_screening) null ~20.4% together — again tracks screenings where no NCD was found (`control_status = 'Not diagnosed'`, 970 rows), not corruption.
- `lab_tests.sample_date`/`result_date`/`result_flag` null 25.59%, matching `test_status == 'Ordered-not-completed'` (513) — the intended "not completed" signal, use `test_status` as the authoritative flag rather than inferring from date nulls.
- `medicine_dispensing`: 978 prescriptions (of 4,209) have **zero** dispensing rows — true non-attempts, must be counted as incomplete medicine access, not silently excluded from the denominator.
- `geography_reference.road_access` has a long tail: 'Paved' 14, 'Mixed' 12, 'Mostly paved' 9, **'Poor' 1** — a single-village category; any road-access breakdown must show the denominator so this 1-village group isn't visually equated with the 14-village group.
- Village free-text noise: 113 distinct strings across operational tables map down to 36 canonical villages — a real linkage task, not something to "clean" by string-lowering alone (confirmed several are genuine misspellings, not just casing).

## 7. Temporal-leakage risks for any future predictive model

- `next_followup_due` (ncd_screening) and `review_due_days`/derived due-dates are **forward-looking** target-adjacent fields — safe as *known-at-consult-time* features (they're advised at the consult) but any field populated only *after* the outcome is known (e.g. `dispense_date`, `result_date`, `visit_date` of the follow-up itself, `outreach` timestamps after the consult) must be excluded from a model predicting the same episode's outcome, or restricted to a defined lookback window strictly before a chosen prediction-time cutoff.
- `visit_history` rows dated on/after a given episode's `consult_date` must never feed that episode's "prior engagement" features — the pipeline filters strictly on `visit_date < consult_date` per episode (see `scripts/build_processed.py`).
- EVALUATION-cohort `lost_to_followup_label`/`dropout_stage_label` are blank in the source file; the pipeline never imputes them and the UI never treats a blank as 0.
